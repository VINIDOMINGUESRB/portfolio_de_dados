# 🏗️ Modelagem Dimensional e Pipeline Analítico (Staging → Marts)

Pipeline de dados de ponta a ponta que simula o trabalho de um analytics
engineer numa operação de e-commerce: partir de tabelas brutas "sujas",
construir camadas de staging e marts em SQL, validar tudo com testes
automatizados e entregar tabelas de métricas prontas para consumo em BI.

## Objetivo

Times de dados raramente recebem dados prontos. O trabalho começa com
tabelas operacionais cheias de inconsistências — nomes de cidade com
capitalização diferente, canais de aquisição nulos, pedidos cancelados
misturados com concluídos — e o papel do analytics engineer é transformar
isso em um modelo confiável, testado e fácil de consumir.

Este projeto reproduz esse fluxo em escala pequena, usando SQLite como
motor (fácil de rodar localmente, sem infraestrutura) e uma estrutura de
pastas que segue a mesma lógica de camadas usada em ferramentas como dbt:

```
raw_*  →  staging (stg_*)  →  marts (dim_*, fact_*, metrics_*)
```

## Por que dados sintéticos

Os dados são gerados por um script próprio (`data_generation.py`), não
baixados de nenhuma fonte externa. Isso foi proposital: o objetivo aqui é
demonstrar modelagem e engenharia de pipeline, não a análise de um
dataset específico — e gerar os dados permite controlar sazonalidade
(pico de Black Friday/Natal), volume e as inconsistências que a camada de
staging precisa resolver, deixando o projeto 100% reprodutível sem
depender de nenhuma API ou download.

## Arquitetura

**Camada raw** — 4 tabelas simulando um banco operacional: `raw_customers`,
`raw_products`, `raw_orders`, `raw_order_items` (~1.500 clientes, 150
produtos, 9 mil pedidos, ~15,6 mil itens, 2024–2025).

**Camada staging** (`models/staging/`) — uma view por tabela raw, cada
uma resolvendo um problema específico: normalização de texto, preenchimento
de nulos, remoção de preços inválidos, cálculo do valor líquido do item.

**Camada marts** (`models/marts/`) — modelo dimensional (star schema):
- `dim_customer`, `dim_product`, `dim_date` — dimensões
- `fact_orders` — fato no grão de pedido, com receita bruta/líquida
- `metrics_monthly_revenue` — receita, pedidos e ticket médio por mês
- `metrics_customer_ltv` — valor histórico e recência por cliente (é a
  tabela que o próximo projeto do portfólio usa para segmentação)

**Testes de qualidade** (`tests/data_quality_tests.py`) — implementam,
em SQL puro, os testes genéricos que o dbt oferece nativamente (unique,
not_null, relationships, accepted_values), já que o ambiente de execução
não tinha o dbt disponível. A run falha (exit code != 0) se qualquer teste
quebrar, do mesmo jeito que aconteceria num pipeline de CI real.

## Como rodar

```bash
cd novo_projeto_03_analytics_engineering
pip install pandas  # única dependência externa
python build_warehouse.py
```

O script gera os dados brutos, roda staging e marts em sequência, executa
os 9 testes de qualidade e imprime um resumo de negócio. O resultado fica
salvo em `warehouse.sqlite` — dá para abrir com qualquer client SQLite
(DBeaver, DB Browser, a extensão do VS Code) e explorar as tabelas.

## Decisões técnicas que valem explicar

- **SCD tipo 1 em `dim_customer`**: o atributo `segment` é sobrescrito a
  cada carga. Para este caso de uso não havia necessidade de reter
  histórico de mudança de segmento — decisão consciente, não esquecimento.
- **`dim_date` gerada por CTE recursiva**, cobrindo exatamente o intervalo
  de datas presente nos pedidos, em vez de hardcoded.
- **Pedidos cancelados/devolvidos entram em `fact_orders`** com uma flag
  (`is_completed`), em vez de serem descartados na origem — quem consome a
  tabela decide se inclui ou não na receita, o que evita perder informação
  na camada de staging.

## Limitações conhecidas

SQLite foi escolhido pela simplicidade de rodar sem infraestrutura extra,
mas não é o motor que eu usaria em produção — um dbt + warehouse
columnar (BigQuery/Snowflake/Redshift) seria o próximo passo natural,
e a estrutura de pastas aqui já foi pensada para migrar sem muito atrito.

## 🇬🇧 English summary

An end-to-end analytics engineering pipeline that mimics a real e-commerce
data stack: raw operational tables with realistic messiness → SQL staging
layer → dimensional marts (star schema) → automated data quality tests,
all running on SQLite for easy local reproduction.

The raw data is generated by a seeded script (not sourced externally) to
keep the project fully reproducible and to control seasonality and data
issues on purpose. The `models/staging` and `models/marts` folders mirror
the layer structure used by tools like dbt, and `tests/data_quality_tests.py`
reimplements dbt's generic tests (unique, not_null, relationships,
accepted_values) directly in SQL/Python. Run `python build_warehouse.py`
to regenerate everything from scratch, including the test suite.
